# Safe CKA practice for Talos Kubernetes

Sixty independent, self-scoring exercises across the five CKA pillars on Kubernetes v1.35/Talos. Nothing contacts a cluster when cloned or tested. Review commands before running; expected context is `admin@lake`. **Do not use on production.**

## Start one task

```bash
make test                                       # offline, mocked API only
./tasks/workloads/W01/setup.sh                  # from any working directory
cat tasks/workloads/W01/task.md                  # original exercise prompt
./tasks/workloads/W01/score.sh --json
./tasks/workloads/W01/teardown.sh                # only this task's namespace
```

The global ID dispatchers are `./scripts/setup.sh W01`, `./scripts/score.sh W01 [--json]`, `./scripts/teardown.sh W01`, `./scripts/reset.sh W01`, `./scripts/restore.sh W01` (restore and teardown are equivalent for newly created task namespaces). `make setup ID=W01` etc. also work. Setup and teardown accept `--yes`, `--prefix NAME`, `--namespace NAME`; `--yes` only acknowledges a nonstandard context. Or export `CKA_LAB_PREFIX` / `CKA_LAB_NAMESPACE` before using a task wrapper. Custom namespaces must begin with `<prefix>-` and be DNS-safe. Default is `cka-practice-<lowercase-id>`; changing prefix changes the default namespace. A task score wrapper automatically supplies that task's state/evidence scope. `scripts/validate.sh` remains the **legacy low-level scorer**: it consumes explicitly exported `CKA_LAB_STATE_DIR`/`CKA_LAB_NAMESPACE`, and its `--task`/`all` options do not infer independent task state. Prefer `scripts/score.sh ID` or task wrappers. No legacy broad setup/teardown/reset remains.

`TASKS.md` indexes all pillars and IDs. Each `tasks/<pillar>/<ID>/` holds its answer-free prompt (`task.md`), separate spoiler walkthrough (`tutorial.md`), three executable lifecycle scripts and any needed `resources/` (seed YAML or offline samples). Browse `SOLUTIONS.md` for the tutorial index; prompts never link to their answers. Shared lifecycle/scorer code stays in `scripts/`. Top-level `fixtures/` and `samples/` remain as legacy test references; task setup and wrapper scoring use adjacent resources instead. `metadata/tasks.tsv` remains the score/mode source (128 total configured points, before capability exclusions). Answers are under `answers/`, separate from prompts. A15 is a live task with its own namespace, seeded audit/warn labels and baseline enforcement exercise; T10 is also live so its read-only Talos investigation has an independently seeded namespaced Pod. Other read-only tasks make no cluster changes.

## Safety

- Live setup creates **only** that task's new namespace with owner, prefix and task labels and seeds only adjacent task resources. It never adopts a pre-existing namespace, even if labelled. Repeating setup reseeds its own mutable manifests and safely replaces only its own immutable starter Pod(s); W03 establishes a valid revision before the failed rollout. Namespace and state are distinct per ID and custom namespace. Local state and evidence live in `.lab/<ID>/<namespace>/` (mode 0700, state mode 0600); never commit `.lab` or credentials.
- Teardown verifies persisted `namespace_existed=false`, exact namespace UID, task/prefix labels, context and API server. A missing, damaged or mismatched state file fails closed, even with `--yes`. It discovers namespaced APIs and refuses unowned or differently-task-labelled workloads. Kubernetes-generated Events, built-in default ServiceAccount/kube-root CA and controller-owned children are recognized; API discovery failures block deletion. It deletes **only that task's namespace**, never another namespace or a cluster-scoped resource. Deletion of a pre-existing namespace is never supported; use a different namespace. A state lost between namespace creation and state recording requires manual inspection/recovery, never automatic adoption.
- All claims in the namespace and PVs bound to the namespace (including unlabelled storage) block automatic cleanup, regardless of `--yes`. Inspect data, backups, reclaim policy and provisioned volumes before manually deleting Pod/PVC and inspecting remaining PVs. Setup also refuses to reseed while storage exists. Cluster-scoped PV, CRD, RBAC, StorageClass, Talos configuration, nodes and `kube-system` are never modified by setup or teardown.
- New live objects require labels `cka-lab.io/owner=cka-talos-practice` **and** `cka-lab.io/task=<ID>` (also on Pod templates). Do not put unrelated workloads in a task namespace. Restore/reset do not restore snapshots or persistent data. Reset clears only the selected task instance's local evidence (and A08 working overlay); for live tasks it first verifies and tears down that namespace, then seeds a new instance. Offline reset clears only that instance's evidence without contacting the cluster. Teardown alone retains evidence. Namespace deletion is not a backup.
- Pure offline simulations and disposable-kubeadm placeholders do not contact Kubernetes at setup. Read-only exercises query the cluster but create no namespace. A15's isolated namespace exception is explicitly `live` in metadata. Kubeadm init/join/upgrade procedures in the spoiler tutorials are only for isolated, snapshot-backed Ubuntu/Debian VMs; verify VM identity before privileged commands. Never run them on Talos, Proxmox-managed Talos nodes, or this homelab. Talos destructive operations require a separate disposable, snapshot-backed Talos lab.

Prerequisites: Bash 4+, kubectl, Python 3 with PyYAML, awk, grep, sed and a current kubeconfig for live tasks; `make test` never uses a live cluster. Optional helm, talosctl, metrics, controllers and dynamic storage are capability-gated. `PASS/PARTIAL/FAIL` count the two task criteria; `SKIP` and `UNSUPPORTED` remove points from the denominator. Scoring is read-only; exit status is nonzero unless all applicable points are earned. A07 chart needs Helm; setup records Helm availability but never installs it.

Dynamic storage S03/S05 requires operator review of a **disposable** class, reclaim Delete policy, backups and cleanup plan. Set `CKA_LAB_STORAGE_CLASS=<class> CKA_LAB_STORAGE_APPROVED=true` on each task's setup. S03 requests exactly 64Mi; S05 independently creates a 64Mi claim in its own namespace and expands to exactly 128Mi. The scorer checks the requested/bound size and receipt but cannot prove historical transitions. No setup creates a PVC; cleanup cannot delete PVC/PV automatically. If a capability is absent it is `SKIP`. No default StorageClass is implicitly approved. NetworkPolicy/Gateway/Ingress, read-only Talos and Helm are similarly gated or simulated rather than installed.

`make test` checks task metadata, executable bits, local fixture scope, mocked independent lifecycles and negative/positive scorer cases. A real cluster smoke test should only happen after reviewing the scope and target context. `git diff --check` and pre-commit secret scanning are part of contributor verification.
